# user-scenarios

## Правило маркировки

Каждый сценарий помечается применимостью: `[v1]`, `[v2]`, `[v1+v2]`.

## Сценарии

### [v1] Сценарий A: первичная настройка workspace

1. Пользователь или администратор задает `raw_path` и `output_path`.
2. Запускает `anonym doctor`.

Ожидаемый результат:
- CLI подтверждает корректные пути, доступ к API и наличие секретов;
- `api.partner_id` валидируется как UUID и совпадает с партнером, выданным владельцем API;
- все runtime-команды (`scan/list/run/doctor`) используют единое правило UUID-валидации `api.partner_id`;
- preflight сообщает о нарушении boundary/ACL, если окружение небезопасно.

### [v1+v2] Сценарий B: ежедневный поток

1. Пользователь запускает `anonym scan`.
2. Пользователь запускает `anonym list`.
3. Пользователь выбирает `id` и запускает `anonym run <id>`.

Ожидаемый результат:
- в `output_path` появляется новый анонимизированный файл с безопасным именем;
- исходный файл в `raw_path` не удаляется и не перемещается.

### [v1+v2] Сценарий C: запуск по точному имени или относительному пути

1. Пользователь запускает `anonym run <relative_path>`.
2. CLI ищет файл только в пределах `raw_path`.

Ожидаемый результат:
- при точном совпадении обработка начинается;
- при отсутствии файла CLI показывает понятную ошибку и подсказки.

### [v1+v2] Сценарий D: запуск по примерному имени

1. Пользователь запускает `anonym run invoice april`.
2. CLI ищет совпадения только в пределах `raw_path`.

Ожидаемый результат:
- одно совпадение: обработка запускается;
- несколько совпадений: CLI показывает кандидатов с `id`, запуск не выполняется до явного выбора;
- нет совпадений: CLI предлагает похожие варианты.

### [v1] Сценарий E: preflight и безопасное обнаружение без отправки

1. Пользователь запускает `anonym doctor`.
2. Пользователь запускает `anonym scan`.
3. Пользователь запускает `anonym list`.

Ожидаемый результат:
- preflight подтверждает или блокирует запуск по правилам boundary/ACL и секретов;
- `scan` обнаруживает только файлы внутри `raw_path`;
- `list` показывает локальную очередь с техническими идентификаторами и статусами;
- отправка файлов в API на шагах `scan/list` не выполняется.

### [v1] Сценарий F: явный запуск run с обновлением статусов

1. Пользователь выполняет `anonym scan`.
2. Пользователь выполняет `anonym run <id|path>`.
3. Пользователь проверяет состояние через `anonym list`.

Ожидаемый результат:
- отправка в API выполняется только на шаге `run`;
- вызов `POST /v1/tasks/file_anonymization` уходит с `Authorization`, `partner-id` и `fields=anonymizer`;
- при неоднозначном fuzzy-поиске CLI выводит кандидатов и требует явный `id`;
- при успешной обработке создается выходной файл в `output_path` с техническим именем без исходного raw-имени;
- статус элемента в каталоге обновляется до `succeeded` или `failed`.
- в audit-журнале `<workspace>/.anonym/audit.log` фиксируется безопасная запись с HMAC `file_id`.
