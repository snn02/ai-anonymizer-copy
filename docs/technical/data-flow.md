# data flow

## `doctor`

1. Загрузка конфига.
2. Проверка `raw_path`/`output_path`.
3. Проверка boundary и platform-ограничений.
4. Проверка секретов в OS secret store.
5. Проверка сетевого подключения к allowlisted API.
6. Вывод итогового статуса и рекомендаций.

## `scan`

1. Проход по `raw_path` в рамках pathguard-политики.
2. Обновление каталога кандидатов.
3. Фиксация безопасных метаданных.

## `list`

1. Чтение локального каталога.
2. Вывод `id`, статусов и служебной информации без PII.

## `run <id|path|fuzzy>`

1. `resolver` определяет ровно один файл-кандидат.
2. `pathguard` повторно валидирует путь.
3. Применяются лимиты (`max_file_size`, `max_pages`, timeout, `max_parallel_runs`).
4. Запрос уходит в `POST /v1/tasks/file_anonymization`.
5. Результат нормализуется адаптером контракта.
6. Анонимизированный файл сохраняется в `output_path`.
7. Каталог и аудит обновляются.

## Инварианты потока

- Отправка в API никогда не выполняется в `scan`.
- Raw-файл не удаляется и не перемещается.
- Любой отказ возвращает понятный код и следующий шаг.
