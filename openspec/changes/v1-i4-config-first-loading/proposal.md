# proposal: v1-i4 config first loading

## Контекст

После обновления документации `v1` базовый пользовательский сценарий зафиксирован как config-first:
1. параметры runtime должны задаваться через `config.yaml` как основной источник;
2. override допускается точечно через env или CLI;
3. приоритет источников должен быть детерминированным: `CLI > env > config file`.

Текущий runtime не соответствует этому контракту, потому что путь `--config` не приводит к фактической загрузке значений из YAML.

## Цель итерации

Довести runtime-конфигурацию `v1` до рабочего config-first режима без изменения API-контракта:
1. `config.yaml` реально участвует в загрузке параметров для `doctor/scan/list/run`;
2. сохраняется и тестами подтверждается приоритет `CLI > env > config file`;
3. `user-guide` переводится на приоритетный сценарий компактного запуска через конфиг.

## In Scope

1. Реализация чтения `config.yaml` в `internal/config` для runtime-параметров `v1`.
2. Поддержка нестандартного пути к конфигу через `--config`.
3. Тесты на приоритет источников и ошибки парсинга/чтения конфига.
4. Синхронизация документации (`user-guide`, `technical/configuration`, сценарии, action-log) под config-first сценарий.
5. Трассировка `requirement -> task -> test -> runtime evidence` в OpenSpec-артефактах.

## Out Of Scope

1. Изменения контрактов API (`/v1/tasks/*`) и заголовков runtime `v1`.
2. Добавление новых runtime-команд или расширение поведения `run` вне конфигурационного слоя.
3. Любые задачи `v2` и MCP-расширения.

## Критерии Приемки

1. При валидном `config.yaml` команды `doctor/scan/list/run` работают без дублирования полного набора runtime-флагов.
2. При конфликте значений подтверждается приоритет `CLI > env > config file`.
3. Ошибки чтения/парсинга `config.yaml` возвращаются в явном диагностируемом виде.
4. Документация `v1` описывает config-first как основной сценарий и отдельные случаи override через env/CLI.
