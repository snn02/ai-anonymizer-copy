# agents

## Назначение

Правила работы агентов при разработке и сопровождении документации проекта.

## Источник структуры документации

- Основная карта: `docs/doc-map.md`.
- Если есть конфликт между файлами, приоритет у более конкретного документа версии (`docs/versions/<version>/plan.md`) над общим описанием.

## Обязательные действия агента при изменениях в разработке

1. Сначала определить, к какой версии относится изменение: `v1` или `v2`.
2. Обновить требования версии:
   - `docs/versions/<version>/plan.md`.
3. Обновить сценарии при изменении поведения:
   - пользовательские: `docs/user-scenarios.md`;
   - тестовые: `docs/test-scenarios.md`.
4. Зафиксировать изменения в журнале версии:
   - `docs/versions/<version>/action-log.md`.
5. Если принято новое правило/политика, добавить запись в:
   - `docs/decisions.md`.

## Правила для тестовых сценариев

- При добавлении/изменении теста указывать:
  - применимость по версии (`[v1]`, `[v2]`, `[v1+v2]`),
  - приоритет (`p0`, `p1`, `p2`).
- Для `v1` release gate обязателен:
  - все `p0`-сценарии с метками `[v1]` и `[v1+v2]` должны быть `pass`.

## Правила для openapi и контрактов

- При изменении интеграционного контракта сверять описание с `docs/openapi.json`.
- Если поведение API неоднозначно, фиксировать адаптерное поведение и ожидаемые тесты в `docs/versions/<version>/plan.md` и `docs/test-scenarios.md`.

## Правила для openspec

- `openspec` находится в корне проекта: `openspec/`.
- Для `v1` workflow согласован:
  - feature-пакеты в `openspec/changes/` создаются по одной итерации;
  - одна итерация = законченный и тестируемый результат.
- Для `v2` feature-пакеты создаются после отдельного решения по старту `v2`.

## Итерационный workflow для v1

1. Сформировать/уточнить общий план `v1` в `docs/versions/v1/plan.md`.
2. Спланировать текущую итерацию с четким тестируемым результатом.
3. Создать feature-пакет итерации в `openspec/changes/`.
4. Реализовать итерацию и выполнить тесты по приоритетам.
5. Зафиксировать выводы в `docs/versions/v1/action-log.md` и запланировать следующую итерацию.
6. После завершения всех итераций `v1`: общее тестирование, релиз, обновление `docs/lessons-learned.md`.

## Правила качества документации

- Все файлы и папки документации ведутся в `lowercase`.
- Документация ведется на русском языке.
- Все файлы документации сохраняются строго в `UTF-8` (предпочтительно `UTF-8 with BOM` для совместимости с Windows/PowerShell).
- При изменении документов агент обязан явно указывать `UTF-8` в командах чтения/записи и проверять diff на отсутствие проблем кодировки (кракозябр).
- Формулировки должны быть проверяемыми:
  - избегать только деклараций «должно быть безопасно» без критерия проверки.
- Нельзя оставлять несинхронизированные изменения между:
  - `plan.md`, `user-scenarios.md`, `test-scenarios.md`, `action-log.md`.

## Что делать при закрытии версии

1. Обновить `docs/versions/<version>/action-log.md` итоговой записью.
2. Перенести ключевые выводы в `docs/lessons-learned.md`.
3. Обновить статус версии в `docs/roadmap.md`.

## Запрещено

- Вносить изменения в реализацию без отражения в релевантной документации.
- Добавлять новые документы вне структуры из `docs/doc-map.md` без причины и записи в `docs/decisions.md`.
- Создавать feature-спеки для `v2` без отдельного решения о старте `v2`.
